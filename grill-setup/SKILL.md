# Grill Setup

데이비드의 일반 업무 프로젝트(코딩이 아닌 — 딜, 법무, 운영, 리서치 등)를 위한 지식 구조를 스캐폴딩한다. 다른 스킬들과 미래의 자기 자신이 일관되게 참조할 수 있도록 다음을 세팅한다:

- **도메인 (추천 엔진)**: 이 프로젝트가 어떤 종류인가 — 가장 먼저 정하고, 도메인에 맞는 knowledge 구조·지표·어휘를 Claude가 *추천*하며, 이 답이 나머지 항목의 기본값을 바꾼다
- **Todo / 작업 트래커**: 이 프로젝트의 할 일은 어디에서 관리하는가
- **Priority / Status 어휘**: 어떤 우선순위/상태 단어를 쓰는가
- **도메인 문서 레이아웃**: `CONTEXT.md` 하나(단일)인가, 멀티 컨텍스트 레이아웃인가
- **목표 / 마감**: 이 프로젝트의 "done"이 무엇이고 핵심 데드라인은 언제인가
- **데이터 소스 & 초기 ingest**: Slack/Notion/Drive 등에서 자료를 가져올 곳을 기록하고, 지금 바로 끌어와 시드할지 정한다 (전 도메인 공통)
- **(조건부) 인물·지표·민감도·리뷰 리듬**: 도메인 레시피가 켠 것만 묻는다

그리고 형제 스킬(`grill-knowledge`, `grill-sync`)이 읽고 쓰는 **4개 위치 — `CONTEXT.md`(용어 사전), `docs/adr/`(의사결정 기록), `STATUS.md`(휘발성 상태), Iron Law(강제 룰) — 를 빠짐없이 골격으로 만든다**. setup이 만들지 않은 곳에 다른 스킬이 쓰려다 위치가 어긋나는 일을 막는다.

이건 결정론적 스크립트가 아니라 **대화 기반 스킬**이다. 탐색 → 발견한 것 제시 → 사용자 확인 → 쓰기, 이 순서로 진행한다.

## Process

### 1. Explore

현재 폴더 상태를 파악한다. 가정하지 말고 실제로 읽어볼 것:

- `CLAUDE.md` — 이미 존재하는가? 어떤 내용이 들어있는가? `## Agent skills` / `## Iron Laws` 섹션이 이미 있는가?
- `CONTEXT.md` — 존재하는가?
- `CONTEXT-MAP.md` — 존재하면 이미 멀티 컨텍스트로 운영 중이라는 신호
- `STATUS.md` — 휘발성 상태 파일이 이미 있는가? (있으면 목표/마감만 보강, 덮어쓰지 말 것)
- `docs/agents/` — 이 스킬의 이전 산출물이 있는가?
- `docs/adr/` — 의사결정 기록이 쌓여 있는가?
- `docs/knowledge/` — 참조용 지식 자료가 있는가? (`people.md` 등)
- 폴더 내 하위 프로젝트(예: `wwg-deal/`) — 자기 자신의 `CLAUDE.md`나 `CONTEXT.md`를 갖고 있는가?

### 2. Present findings and ask

발견한 것을 짧게 요약해서 사용자에게 보여준다. 그 다음 **결정을 한 번에 하나씩** 사용자와 함께 한다. 한꺼번에 던지지 말 것 — 사용자가 답한 뒤에 다음으로 넘어간다.

> **운영 원칙 — 결정하지 말고 질문하라 (가장 중요)**
>
> 이 스킬은 스스로 판단해 구조를 확정하지 않는다. 구조적 갈림길(도메인 분류, 멀티 그룹 여부와 분할 축, 히스토리를 어디에 둘지, 어떤 knowledge 파일을 만들지)은 **전부 질문으로 사용자가 정한다.**
>
> - 레시피·기본값·추천은 *자동 적용되는 답*이 아니라 **질문의 출발점(메뉴)**이다. "X로 해두겠습니다"가 아니라 "보통 X를 쓰는데, X로 갈까요 아니면 다르게 할까요?"로 제시한다.
> - 확신이 낮은 칸은 추측으로 채우지 말고 비워서 묻는다. 모르면 "이건 제가 정하기 애매한데, 어떻게 할까요?"라고 한다.
> - 예외: 사용자가 명시적으로 "알아서 해줘 / 추천대로 가"라고 하면, 그때만 추천안을 그대로 적용하고 무엇을 정했는지 사후 보고한다.
> - 묻는 횟수가 부담되면 관련 갈림길을 하나의 질문에 모아 선택지로 제시한다. 단, 임의로 생략하고 결정해버리지는 않는다.

> **질문 순서 — 반드시 이 순서로 (어기지 말 것)**
>
> 큰 결정부터 작은 결정으로 내려간다. 세부(파일·지표 등)부터 묻지 말 것.
>
> 1. **어떤 종류의 프로젝트인가** (도메인 확인) — "마케팅 맞나요?"
> 2. **하나로 관리할까, 여러 그룹으로 나눌까** (단일/멀티) — 나눈다면 무슨 기준으로(채널별·월별 등). **이 질문을 세부보다 먼저 한다.**
> 3. 그 다음에야 **무엇을 기록할지 / 어떤 숫자를 볼지 / 진행 단계 이름 / 히스토리 위치 / 목표·마감 / 데이터 가져오기** 등 세부로 들어간다.
>
> 스크린샷처럼 "어떤 파일 만들까?"를 1·2번보다 먼저 묻는 건 잘못. 1·2를 확정한 뒤 세부를 묻는다.

> **쉬운말 원칙 — 전문용어·파일명을 선택지로 쓰지 말 것**
>
> 질문과 선택지는 비개발자도 바로 이해할 쉬운 말로 쓴다.
>
> - 선택지 라벨에 파일명(`campaign-history.md`)이나 영어 약어(ROAS, CAC, TTH)를 그대로 쓰지 말 것. 대신 풀어서 쓴다 — "캠페인 기록 (언제 무슨 캠페인을 했는지)", "성과 숫자 (광고비 대비 매출 등)".
> - 실제 파일명·필드명은 **사용자가 개념을 고른 뒤 Claude가 내부적으로** 정한다. 사용자에게 보여줄 필요 없다.
> - "컨텍스트", "멀티 컨텍스트", "ingest", "harness" 같은 스킬 내부 용어도 사용자 앞에서는 풀어 쓴다 — "하나로 볼지 나눌지", "기존 자료 가져오기" 등.

**순서가 중요하다**: 위 "질문 순서"를 따른다. 섹션 0(도메인)과 단일/멀티를 **가장 먼저** 확정한 뒤 나머지를 묻는다.

각 섹션은 짧은 설명(이게 뭐고, 왜 필요하고, 선택에 따라 뭐가 달라지는지)으로 시작한다. 그 다음에 선택지를 쉬운 말의 질문 형태로 제시한다.

사용자가 이 용어들을 모른다고 가정한다.

---

**섹션 0 — 도메인 (추천 엔진)**

> **설명**: 이 프로젝트가 어떤 종류인지를 가장 먼저 정한다. 도메인을 알면 그 도메인에서 흔히 쓰는 지식 구조(어떤 knowledge 파일, 어떤 지표, Status 어휘, 단일/멀티)를 Claude가 *후보로 제시*할 수 있다. 단, 이건 추천이지 결정이 아니다 — **운영 원칙대로 전부 질문으로 사용자가 고른다.**

**동작 방식 (질문 순서를 지킨다)**:

1. **도메인 확인** — 사용자에게 어떤 종류의 프로젝트인지 묻거나, 맥락에서 짐작되면 "마케팅 프로젝트 맞나요?"로 확인한다.
2. **단일/멀티 먼저** — 세부로 들어가기 전에 "이 프로젝트를 하나로 관리할까요, 여러 그룹으로 나눌까요?"를 묻는다. 나눈다면 무슨 기준인지(예: 채널별, 캠페인별, 월별)까지. **이게 두 번째 질문이다 — 파일·지표 같은 세부보다 먼저.**
3. **그 다음 세부** — 1·2가 정해진 뒤에야 무엇을 기록할지·어떤 숫자를 볼지·진행 단계 이름 등으로 들어간다. 이때 아래 레시피를 *쉬운 말로 풀어* 후보로 보여주고 고르게 한다.
4. 사용자가 고른 결과만 채택한다. 추천을 그대로 적용하는 건 사용자가 "추천대로 가"라고 할 때뿐이다.

**워크플로 예시 — "마케팅 셋팅해줘"** (순서·쉬운말 모두 지킨 모습):

> 1. "마케팅 프로젝트군요, 맞나요?"
> 2. "이걸 **하나로 관리할까요, 아니면 채널·캠페인별로 나눠서** 관리할까요? 월별로 기록을 쌓고 싶으면 그렇게도 가능해요."
> 3. (위가 정해진 뒤) "그럼 무엇을 기록해둘까요? 보통 마케팅은 이런 걸 모아둬요 — 골라주세요:
>    - 캠페인 기록 (언제 무슨 캠페인을 했는지)
>    - 성과 숫자 (광고비 대비 매출, 신규 고객 획득 비용 등)
>    - 소재 모음 (이미지·카피 등)"
> 그리고 진행 단계 이름(기획→제작→운영중→회고)·목표·마감·기존 자료 가져오기를 차례로 묻는다.

즉 마케팅이라고 해서 Claude가 구조를 정해버리지 않고, **도메인→단일/멀티→세부 순서로, 파일명 대신 쉬운 말로** 묻는다.

**도메인 레시피** (질문의 출발점 — 자동 적용 금지):

> 이 표의 파일명·영어 약어는 **Claude 내부 참고용**이다. 사용자에게 물을 때는 쉬운말 원칙에 따라 풀어서 말한다 — 예: `campaign-history.md` → "캠페인 기록", `metrics.md`+`ROAS/CAC` → "성과 숫자(광고비 대비 매출 등)", `assets.md` → "소재 모음". 사용자가 개념을 고르면 그때 Claude가 파일명을 붙인다.

| 도메인 | 추천 knowledge 파일 / 구조 | 추천 지표 | Status 어휘 | 컨텍스트 | 민감도 |
|---|---|---|---|---|---|
| **마케팅** | `campaign-history.md`(캠페인 히스토리), `metrics.md`(지표 정의), `assets.md` 또는 `creative/`(소재 라이브러리) | ROAS, CAC, CVR, CTR, 채널별 매출 | 기획 / 제작 / 운영중 / 회고 | 채널·캠페인별 멀티 제안 | 일반 |
| **채용** | `pipeline.md`(후보 파이프라인), `roles.md`(JD/요건), `interview-notes.md` | 단계별 전환율, TTH(time-to-hire), 오퍼 수락률 | 소싱 / 인터뷰 / 오퍼 / 클로즈 | 단일 (직무 많으면 멀티) | 기밀 |
| **PR / 커뮤니케이션** | `narrative.md`(메시지·포지셔닝), `media-list.md`(기자·매체), `coverage.md`(보도 추적) | 보도 건수·톤, 노출/리치, 메시지 도달 | 초안 / 검토 / 배포 / 모니터링 | 단일 (위기대응이면 멀티) | 기밀 |
| **제품** | `prd.md`(요구사항), `roadmap.md`, `feedback.md`(사용자 피드백) | 채택률, 리텐션, NPS, 핵심 지표 | 발견 / 정의 / 빌드 / 출시 | 기능·트랙별 멀티 제안 | 일반 |
| **딜 (M&A/투자/제휴)** | `people.md`(인물·회사), 트랙별 `CONTEXT.md`(법무/재무/협상) | 밸류에이션, 마일스톤, 조건 | 탐색 / 협상 / 실사 / 클로징 | 멀티 제안 | 기밀 |
| **법무 (케이스/계약)** | `people.md`(당사자), `cases.md`(쟁점·경과) | 마감·기한, 리스크 등급 | 검토중 / 회신대기 / 종료 | 단일 (트랙 많으면 멀티) | 기밀 |
| **운영 (실행/관리)** | (도메인 특화 없음 — 기본 구조) | (필요 시 사용자 정의) | 기본 (Not started / In progress / Done) | 단일 | 일반 |
| **리서치 (조사/분석)** | `sources.md`(출처), `findings.md`(발견), `questions.md`(미해결 질문) | (정성 위주 — 필요 시 정의) | 기본 | 단일 | 일반 |

**미등록 도메인 생성 규칙**: 표에 없는 도메인(예: "이벤트 기획", "투자자 관계", "고객 성공")이면, Claude가 그 도메인의 핵심 산출물을 떠올려 같은 4칸(knowledge 파일 / 지표 / Status 어휘 / 컨텍스트·민감도)을 채운 추천 초안을 만든다. 확신이 없는 칸은 비워두고 사용자에게 묻는다. 추측을 사실처럼 제시하지 말 것 — "이 도메인은 보통 이런 구조를 쓰는데, 맞나요?"로 제안한다.

**단일/멀티 질문 (도메인 확인 직후, 세부보다 먼저 — 질문 #2)**: "이 프로젝트를 하나로 관리할까요, 여러 그룹으로 나눌까요?"를 **파일·지표 같은 세부를 묻기 전에** 한다. 나눈다면 **어떤 기준으로 나눌지**까지 정한다(쉬운말로: "채널별로? 캠페인별로? 월별로?"). 레시피의 "컨텍스트" 칸이 기본 제안 기준이다:

- **단일** — 그룹 없음. 대부분의 작은 프로젝트.
- **트랙별** — 예: 딜(법무/재무/협상), 제품(기능 트랙). 트랙마다 자체 `CONTEXT.md` + `docs/adr/`.
- **채널·캠페인별** — 예: 마케팅(채널/캠페인마다 그룹).
- **시간별 (월별/분기별)** — 히스토리를 누적 관리할 때. `history/2026-01.md`, `history/2026-02.md` … 처럼 기간 단위로 기록을 모은다. "월별로 기록 쌓고 싶다"는 요구가 여기에 해당. (자세한 레이아웃은 섹션 C)

확신이 안 서면 단일로 시작하라고 권하고, 나중에 분할로 마이그레이션할 수 있음을 알린다.

도메인·채택된 레시피·그룹 축은 `docs/agents/domain.md` 상단과 `CLAUDE.md`의 `## Agent skills`에 기록한다. 추천된 knowledge 파일들은 섹션 4에서 골격으로 생성한다.

**섹션 A — Todo / 작업 트래커**

> **설명**: "작업 트래커"는 이 프로젝트의 할 일이 어디에 있는지를 의미한다. 미래의 다른 스킬들 (예: "오늘 할 일 보여줘", "이 메일에서 액션 아이템 등록해줘") 이 어디를 봐야 할지 알아야 한다. 데이비드는 보통 Notion을 쓰지만, 프로젝트마다 다를 수 있다.

기본 자세: 데이비드의 메인 Todo DB가 Notion에 있으므로 그걸 기본값으로 제안한다. 다른 옵션:

- **Notion (David's Todo List)** — `https://www.notion.so/35dd4a5a601f805daca1eb39ca2c8f1c` 의 통합 DB에서 관리. Data Source: `collection://35dd4a5a-601f-8053-b432-000b0bf54abb`
- **로컬 markdown** — 이 폴더 안의 `tasks/` 또는 `inbox.md`에서 관리 (작은 프로젝트나 Notion과 분리하고 싶을 때)
- **별도 Notion DB** — 이 프로젝트 전용의 다른 Notion DB가 있다면 URL과 Data Source ID를 받는다
- **기타** (Linear, Asana, 메일 inbox 등) — 사용자가 워크플로를 한 문단으로 설명; 스킬이 freeform prose로 기록

**섹션 B — Priority / Status 어휘**

> **설명**: 데이비드의 Notion Todo DB는 `Priority`(High/Medium/Low)와 `Status`(Not started/In progress/Done) 필드를 쓴다. 하지만 프로젝트마다 다른 어휘가 필요할 수 있다 (예: 법무 케이스는 "검토중/회신대기/종료", 딜은 "탐색/협상/실사/클로징"). 미래의 다른 스킬이 라벨을 잘못 만들지 않도록 여기 매핑해둔다.

**기본값은 섹션 0의 도메인 preset에서 가져온다.** 운영/리서치/기타는 아래 Notion Todo와 동일한 기본값을, 딜·법무는 도메인 전용 어휘를 제안한다.

기본값 (운영/리서치/기타 — Notion Todo와 동일):

- Priority: `High` (마감 임박/타인 대기/딜·계약·법무 영향), `Medium` (중요하지만 며칠 여유), `Low` (참고용)
- Status: `Not started`, `In progress`, `Done`

도메인 전용 어휘 예시:

- 딜: Status = `탐색` / `협상` / `실사` / `클로징`
- 법무: Status = `검토중` / `회신대기` / `종료`

사용자가 오버라이드하고 싶은 게 있는지 묻는다. 기본이 맞으면 그대로 둔다. 프로젝트별 특수 상태(예: WWG 딜에 "인사이트 회신대기" 같은 게 자주 나오면)가 있으면 추가로 기록.

**섹션 C — 도메인 문서 레이아웃 (그룹 축 확정)**

> **설명**: 섹션 0에서 사용자가 고른 그룹 축(단일 / 트랙별 / 채널·캠페인별 / 시간별)을 실제 폴더 레이아웃으로 보여주고, 추가 갈림길(특히 히스토리 위치)을 질문으로 확정한다. 어떤 스킬들은 `CONTEXT.md`를 읽어 용어를 학습하고 `docs/adr/`에서 과거 결정을 본다. 그룹으로 나누면 각 그룹이 자체 `CONTEXT.md` / `docs/adr/`를 갖는다.

**그룹 축은 섹션 0에서 사용자가 이미 골랐다.** 여기서는 그 축에 맞는 폴더 구조를 보여주고, Claude가 임의로 정하지 말고 사용자에게 확인받는다.

- **단일** — 루트에 `CONTEXT.md` 하나 + `docs/adr/` 하나. 대부분의 프로젝트가 이쪽.
- **트랙별 멀티** — 루트 `CONTEXT-MAP.md`가 각 트랙의 `CONTEXT.md`를 가리킴:

```
/
├── CONTEXT-MAP.md
├── docs/adr/                  ← 프로젝트 전체 결정
├── legal/
│   ├── CONTEXT.md
│   └── docs/adr/              ← 법무 트랙 결정
├── finance/
│   ├── CONTEXT.md
│   └── docs/adr/
└── negotiation/
    ├── CONTEXT.md
    └── docs/adr/
```

- **채널·캠페인별 멀티** — 위와 같되 그룹 폴더가 `channel-meta/`, `campaign-spring/` 식.
- **시간별 (월별/분기별 히스토리)** — 누적 기록을 기간 단위로 모은다. `CONTEXT.md`와 `docs/adr/`는 루트에 하나로 두고, 히스토리만 기간 파일로 쌓는다:

```
/
├── CONTEXT.md                 ← 용어는 단일 유지
├── STATUS.md
├── docs/adr/
└── history/
    ├── 2026-01.md             ← 1월 기록
    ├── 2026-02.md             ← 2월 기록
    └── ...
```

  각 월 파일에는 그 달의 주요 사건·지표·결정을 모은다. 매달 새 파일을 추가하며, 과거 파일은 수정하지 않고 보존한다(히스토리). 섹션 E에서 ingest를 "지금" 선택하면 이 월별 파일들을 과거 자료로 채울 수 있다.

**히스토리 위치 질문 (히스토리를 쌓을 프로젝트면 반드시 묻는다)**: "과거 기록(히스토리)을 어디에 둘까요?" Claude가 정하지 말 것 — 아래에서 사용자가 고른다:

- **루트 `history/<YYYY-MM>.md`** — 프로젝트 전체를 하나의 타임라인으로. 시간별 그룹을 골랐을 때 자연스러움.
- **각 서브 그룹 안 `<group>/history/`** — 멀티 그룹(트랙별/채널별)일 때, 그룹마다 자기 히스토리를 따로. 예: `channel-meta/history/2026-01.md`, `legal/history/`.
- **`docs/knowledge/` 밑** — 히스토리를 "참조 지식"으로 취급. `docs/knowledge/history.md`(짧으면 한 파일) 또는 `docs/knowledge/history/2026-01.md`(월별로 쌓을 거면 폴더).
- **따로 두지 않음** — `STATUS.md`와 `docs/adr/`로 충분한 경우.

선택 기준 힌트(질문에 곁들임): 멀티 그룹이고 그룹마다 흐름이 다르면 → 서브 그룹 안. 프로젝트 전체 타임라인이 중요하면 → 루트 `history/`. 가끔 들춰보는 참고용이면 → `docs/knowledge/`. 사용자가 고른 위치를 `docs/agents/domain.md`에 기록한다.

확신이 안 서면 단일로 시작하라고 권한다. 나중에 분할로 마이그레이션할 수 있다.

**섹션 D — 목표 / 마감**

> **설명**: 이 프로젝트의 "done"이 무엇인지(무엇이 완료되면 끝인가)와 핵심 데드라인을 한 번 박아둔다. 우선순위 판단의 기준점이 되고, 미래 스킬이 "지금 뭐가 급한가"를 판단할 때 참조한다. 이 내용은 `STATUS.md` 상단에 들어간다.

물어볼 것:

- **목표 (done의 정의)**: 이 프로젝트가 무엇을 달성하면 완료인가? 한두 문장.
- **핵심 마감 / 마일스톤**: 절대 놓치면 안 되는 날짜가 있는가? (없으면 "없음"으로 둔다)

답이 모호하면 한 번 더 캐묻되, 사용자가 "아직 모르겠다"고 하면 STATUS.md에 `(미정 — 다음 grilling에서 확정)`으로 남기고 넘어간다.

**섹션 E — 데이터 소스 & 초기 ingest (전 도메인 공통)**

> **설명**: 데이비드의 프로젝트는 시작할 때 Slack 스레드, Notion 페이지, Google Drive 문서 등에서 그동안의 히스토리를 한 번에 가져와 정리하는 일이 많다. 이 섹션은 (1) 이 프로젝트가 들여다볼 데이터 소스가 어디인지 기록하고, (2) 기존 소스의 히스토리를 지금 바로 끌어와 시드할지 정한다. 시간별(월별) 그룹을 골랐다면 가져온 히스토리를 월별 파일로 나눠 담는다. **이 섹션은 도메인과 무관하게 항상 묻는다.**

물어볼 것:

1. **소스 위치**: 이 프로젝트에서 들여다볼 곳은? (Slack 채널·스레드 / Notion 페이지·DB / Google Drive 폴더·문서 / Gmail / BigQuery 등). URL이나 채널명을 받는다. → `docs/agents/domain.md`의 `## 데이터 소스`에 항상 기록한다.
2. **히스토리 ingest할지 (도메인 무관 — 항상 묻는다)**: "기존 소스(Slack/Notion/Drive 등)에서 지금까지의 히스토리를 가져와 정리해둘까요, 아니면 나중에 할까요?" 어떤 도메인이든 이 질문은 한다.
   - **지금** → 지정한 소스에서 자료를 실제로 가져온다. 사용한 커넥터:
     - Slack: `slack_read_channel` / `slack_read_thread` / `slack_search_*`
     - Notion: `notion-fetch` / `notion-search`
     - Google Drive: `search_files` / `read_file_content` / `download_file_content`
     - Gmail: `search_threads` / `get_thread`
     - **히스토리를 쌓는 프로젝트면** → 섹션 C에서 사용자가 고른 히스토리 위치(루트 `history/` / 서브 그룹 안 / `docs/knowledge/` 밑)에 가져온 자료를 날짜 기준으로 갈라 채운다(예: `<선택위치>/2026-01.md`). 그 외에는 `docs/knowledge/ingest-<source>.md` 한 곳에 요약 시드한다.
     - 원문을 통째로 붙여넣지 말고, 인물·결정·날짜·핵심 사실 위주로 정리한다. 범위가 크면 "어디까지 가져올까요?(기간/스레드 수/문서)"를 먼저 확인한다.
     - 민감도가 기밀이면 ingest한 자료에도 Iron Law(외부 공유 금지)가 적용됨을 명시한다.
   - **나중** → ingest는 하지 않고, `docs/agents/domain.md`의 `## 데이터 소스`에 "초기 ingest 예정: [소스]"로 계획만 남긴다. 이후 `grill-knowledge`나 "지금 ingest 해줘" 요청 시 실행.

---

**(조건부) 추가 항목 — 섹션 0의 레시피에 따라 ON된 것만 묻는다**

도메인 레시피가 켠 항목만 묻는다. 전부 묻지 말 것 — 인터뷰가 길어진다.

- **핵심 인물·회사** (딜·법무·채용·PR에서 ON): 이 프로젝트의 주요 등장 인물/회사는? → `docs/knowledge/people.md`(또는 레시피가 지정한 파일)를 시드한다. 이후 grill-knowledge가 채운다.
- **추천 지표 확정** (마케팅·채용·PR·제품에서 ON): 레시피가 제안한 지표(예: 마케팅의 ROAS/CAC/CVR)가 맞는지 확인하고, 맞으면 `docs/knowledge/metrics.md`에 정의를 박는다.
- **민감도 / 기밀 여부** (레시피 기본값에서 가져옴): 기밀이면 외부 공유·publish를 함부로 하지 않도록 Iron Law로 박는다 (`CLAUDE.md`의 `## Iron Laws`).
- **리뷰 리듬** (전 도메인 선택): 매일/매주 다이제스트가 필요한 프로젝트인가? 필요하면 `schedule` 스킬로 정기 작업을 걸자고 제안한다 (파일은 만들지 않음).

### 4. Write

**파일 선택 규칙**:

- `CLAUDE.md`가 이미 존재하면 그걸 편집한다
- 없으면 사용자에게 새로 만들지 묻는다 — 임의로 만들지 말 것
- 기존 `## Agent skills` / `## Iron Laws` 블록이 있으면 **in-place로 업데이트**, 중복 추가 금지
- `STATUS.md`가 이미 있으면 목표/마감만 보강하고 나머지(현재 상태/다음 액션)는 건드리지 말 것
- 사용자가 편집한 다른 섹션은 절대 건드리지 말 것

`CLAUDE.md`에 추가할(또는 업데이트할) 블록 형식:

```markdown
## Agent skills

### 도메인

이 프로젝트는 **[딜 / 법무 / 운영 / 리서치 / 기타]** 프로젝트다. 자세한 내용은 `docs/agents/domain.md` 참조.

### Todo / 작업 트래커

[한 줄 요약 — 어디서 관리하는지]. 자세한 규칙은 `docs/agents/todo-tracker.md` 참조.

### Priority / Status 어휘

[한 줄 요약 — 기본 어휘 또는 커스텀]. 자세한 매핑은 `docs/agents/priorities.md` 참조.

### 도메인 문서 레이아웃

[한 줄 요약 — "단일 컨텍스트" 또는 "멀티 컨텍스트"]. 자세한 규칙은 `docs/agents/domain.md` 참조.

### 휘발성 상태

이 프로젝트의 목표·마감·현재 상태는 `STATUS.md`에 있다. grill-knowledge / grill-sync가 자동 갱신.

## Iron Laws

이 프로젝트에서 반드시 지켜야 하는 강제 룰. 위반하면 안 되는 제약을 여기 박는다. grill-knowledge 스킬이 새 룰을 발견하면 여기 추가한다.

- [기밀 프로젝트인 경우] 이 프로젝트 자료는 외부 공유·publish 금지. 공유 전 반드시 데이비드 확인.
- (그 외 아직 없음)
```

> 기밀이 아닌 프로젝트면 `## Iron Laws`에는 `- (아직 없음)`만 남긴다. 블록 자체는 항상 만들어 둔다 — grill-knowledge가 쓸 자리가 필요하다.

그 다음 `docs/agents/` 폴더에 세 개의 docs 파일을 작성한다. 빈 골격이 아니라 사용자의 답변을 반영한 실제 내용을 채워서 쓴다. 각 파일은 아래 템플릿을 참고:

#### `docs/agents/todo-tracker.md` 템플릿

```markdown
# Todo / 작업 트래커

이 프로젝트에서 할 일은 **[Notion / 로컬 markdown / 기타]** 에서 관리한다.

## 위치

[URL / 폴더 경로 / 설명]

## 스키마 (Notion인 경우)

| 필드 | 설명 |
|---|---|
| `Project name` | 할 일 제목 |
| `Status` | Not started / In progress / Done |
| `Priority` | High / Medium / Low |
| `Start date` | 시작일 (선택) |
| `End date` | 마감일 (선택) |

## 규칙

- 새 액션 아이템이 발견되면 이 트래커에 등록한다
- 작업 시작 시 → `In progress`
- 완료 시 → `Done` + 페이지에 완료 메모
- Done 항목은 삭제하지 않는다 (히스토리)
```

#### `docs/agents/priorities.md` 템플릿

```markdown
# Priority / Status 어휘

## Priority

- **High**: 마감 임박, 다른 사람이 기다림, 딜/계약/법무 영향
- **Medium**: 중요하지만 며칠 여유 있음
- **Low**: 참고용, 나중에 검토해도 됨

## Status

- **Not started**: 아직 시작 전
- **In progress**: 현재 작업 중
```

## harness 모델과 연동 (grill-intake)

grill-setup이 완료된 후 새 작업이 계속 생기면:

- 새 작업 → `grill-intake`로 harness 배치 결정
- 새 harness 신설이 결정되면 → grill-setup을 해당 harness 폴더에서 다시 실행
- 기존 harness sub-epic이면 → grill-setup 불필요, grill-knowledge로 직접 박제
